# 播放队列失败路径回归补强

## Goal

覆盖播放队列在网络失败、存储失败和并发下的行为。队列是用户数据的载体，
失败时静默丢歌或状态错乱的代价远高于搜索结果出错。

## 方法论（沿用上轮，已证明有效）

1. **先测量再改代码**
   - 任何"这是 bug"的判断必须先用可运行的探针证实，不能只靠读代码推断。
   - 上轮我因只读函数开头就误判分页乱序为真 bug，探针证明该路径不可达。
   - 若路径经 UI 不可达，用测试锁住不变量，不为它加生产代码或测试钩子。

2. **新测试必须经变异验证**
   - 每个新回归都要故意破坏对应产品代码，确认测试会失败，然后还原。
   - 上轮有三个"通过"的测试实际抓不住缺陷，全靠变异测试暴露。
   - 断言必须落在被测守卫是唯一防线的路径上，而非某一层实现细节。

3. **失败注入必须真实**
   - 上轮首版离线测试用 `context.setOffline` 无效，因为 `page.route` 的
     fulfill 发生在网络层之前。必须用 `route.abort()` 等真实失败路径。

## Requirements

侦察列出 14 个缺口，本轮取前列三类（详见 `research.md`）：

1. **失败跳歌自愈**：队列唯一的自愈路径，`正在尝试下一首` 在套件里零命中。
   - 一首失败时跳到下一首可播放项，失败项不被跳歌循环回头重试。
   - 全部失败时每项只访问一次并停止，不循环重走队列。

2. **删除正在播放的歌**：`queue_remove` 分支零覆盖。
   - 删中间项：该位置的后继歌接替播放。
   - 删末项：指针 clamp 回队列内，不指向越界位置。

3. **删除播放位置之前的歌**：纯 off-by-one，零覆盖。
   - 同一首歌继续播放（不重新加载），指针随之递减。

## Acceptance Criteria

- [x] 队列顺序与播放位置的读取方式经探针实测确认，不基于假设
- [x] 三处变异（失败集累积、指针递减、末项 clamp）均被测试抓住
- [x] 两处无效变异如实记录，不谎称已验证
- [x] 新增 5 个用例 × 2 视口，全部通过
- [x] 静态契约锁住新增用例标题与关键提示文案
- [ ] 完整 `npm run verify` 十层通过
- [ ] 独立提交、推送、Pages 成功、`npm run check:release` 线上验收

## 安全约束

- 保留用户已有 5 项未提交改动，不暂存、不覆盖、不删除歌单。
- 变异测试改动的产品代码必须全部还原并核对 diff 为空。
- 测试只操作测试专用数据，不触碰用户真实歌单。
- 不强制推送，不改写远端历史。
