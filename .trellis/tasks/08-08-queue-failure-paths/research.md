# 侦察与测量记录：队列失败路径

## 1. 三路并行侦察结果

侦察覆盖：队列失败实现、现有覆盖缺口、测试辅助函数惯例。共列出 14 个缺口，
按用户命中概率与后果排序。本轮取前列的三类（跳歌自愈、删除正在播放的歌、
删除播放位置之前的歌）。

现有覆盖基线：`queue-roundtrip.spec.mjs` 仅 2 个用例且都是成功路径。
`正在尝试下一首` 在整个 e2e 套件里零命中——队列唯一的自愈路径完全没有覆盖。

## 2. 被实测推翻的两处假设

### 队列顺序不是搜索顺序

我最初假设连续添加三首会得到 `[1,2,3]`。探针实测得到 `[940001,940003,940002]`。

根因在 `insertSongToPlaylist`（js/app.js:8744-8756）：插入位置是 `currentIndex + 1`，
且第 8745 行在 `currentIndex === -1` 时把它设为 `playlist.length - 1`。所以第三次
添加时 `currentIndex` 已是 0，新歌插到索引 1。这是既有语义，不是缺陷。

修正做法：`seedQueue()` 返回从应用读回的真实 id 顺序，所有断言基于它，
不再假设顺序。

### currentIndex 没有暴露到 window

我写了 `window.currentIndex` 断言，全部是 `undefined`——该变量是模块内局部变量
（js/app.js:286），从未挂到 window。这些断言毫无意义，是我的错误。

修正做法：新增 `readPersistedIndex()`，从持久化的队列记录读播放位置。

## 3. 传输层重试导致的请求计数

每首失败歌被请求 2 次，不是 1 次。根因是 `API_REQUEST_RETRIES = 1`
（js/core-utils.js:7），传输层对 5xx 自动重试一次。与上轮搜索分页同源。

修正做法：不把重试次数写死。改为断言"每首歌的尝试是一段连续的访问段"，
用 `visitOrder`（去除相邻重复后的访问序列）证明失败集在累积、候选搜索会终止，
而不是反复回头重走队列。

## 4. 变异测试结果

| 变异 | 结果 |
| --- | --- |
| `failedIndexes` 不累积 | **抓住**：全部失败用例失败，循环终止保护失效 |
| 删除较早歌曲时不递减指针（`-= 0`） | **抓住**：期望 1、实际 2 |
| 删除末项时移除 clamp | 初版**未抓住**——原测试只删中间项，clamp 只在删末项触发。已补一个删末项用例，补后抓住（期望 1、实际 2） |
| 跳歌时不推进 `currentIndex`（6790 行） | 未抓住，且**非有效变异** |
| 跳歌时传入错误 index | 未抓住，且**非有效变异** |

### 为什么后两个不是有效变异

播放位置有三重保护：`playSongAtIndex` 在 8623 行设置、跳歌路径在 6790 行设置、
`loadAndPlaySong` 在 7561-7563 行用 `resolvePlaylistIndexBySongId(song.id)`
从歌曲 id 反查并覆盖传入值。任一处失效，其余仍给出正确结果。

如实标注：跳歌用例里的位置断言守的是"最终播放位置必须与实际播放的歌一致"这条
端到端不变量，**不是**经单点变异验证的。若将来重构反查逻辑使三层同时失效，
它会抓住；但不应声称它已被变异证实。

## 5. 未采纳的缺口与原因

侦察列出的第 4 项（虚拟列表行点击的 display-index 到 playlist-index 映射）
是缺口里最值得做的一项——现有全部队列测试都绕过它直接调 `window.*` API。
但它需要 40 首歌 + 滚动 + 洗牌排列的组合场景，规模超出本轮，单独立项更合适。
