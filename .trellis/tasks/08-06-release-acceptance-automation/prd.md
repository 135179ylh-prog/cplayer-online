# 发布验收自动化与门禁分层

## Goal

把发布后的可靠性验收固化成可重复流程：门禁分层+状态文件、线上 Pages 契约与直接 CDP 自动核对。

## 背景

上一阶段（`08-16-sync-health-inflight-expiry`）的线上验收全部靠人工步骤：手动启动
Chrome、手动读 `build-meta.json`、手动比对缓存名和预缓存哈希、手动记录证据。同时
`npm run verify` 是一条不可分割的长命令，浏览器回归通常超过 8 分钟；外层工具在这
期间超时会把整个门禁报成失败，即使没有任何测试真的失败。

## Requirements

1. **门禁分层可恢复**
   - `npm run verify` 保持十层全跑，覆盖不减少。
   - 每层单独记录状态、退出码、耗时和完整日志。
   - 进程被外部结束的层记为 `interrupted`，不是 `failed`。
   - 提供列出层、查看状态、从未完成层继续三个入口。

2. **线上发布自动核对**
   - 一条命令核对线上 commit、Service Worker、缓存版本、核心资源和预缓存哈希。
   - 预缓存哈希必须按线上实际下发的字节重新计算，不能只读公开元数据里的值。
   - 用直接 CDP 采集运行时证据：页面就绪、controller 接管、active 状态、
     CacheStorage 名称、已缓存核心资源数量。
   - 只启动临时 Chrome 和临时配置目录，不连接浏览器扩展，不动用户标签页，
     结束时清理干净。

3. **保留并加强既有回归**
   - 后台切歌、搜索分页、重试、旧请求污染、脱敏诊断五类回归全部保留。
   - 补上三处已知薄弱点：旧查询首页污染、重试游标、隐藏态切歌后的可见 UI，
     以及健康报告在真实下载路径上的脱敏。

4. **文档与契约**
   - README 说明分层门禁和线上核对命令。
   - `.trellis/spec/frontend/quality-guidelines.md` 固化可重复验收契约。
   - 静态契约锁住新增的层、命令和回归，防止静默回退。

## Acceptance Criteria

- [ ] `npm run verify` 十层通过，单元和浏览器数量不低于上一阶段。
- [ ] `npm run check:release -- --commit=<sha>` 对线上站点全部通过。
- [ ] 独立提交、推送、Pages quality/deploy 均 success。
- [ ] 推送后的线上验收由上述命令给出证据，不靠工作流状态推断。

## 安全约束

- 不删除、覆盖或静默修改用户歌单；保留用户已有 5 项未提交改动。
- 核对报告和任务文档不记录密钥、API 地址、token、账号身份、歌单内容或播放进度。
- 不强制推送，不改写远端历史。
